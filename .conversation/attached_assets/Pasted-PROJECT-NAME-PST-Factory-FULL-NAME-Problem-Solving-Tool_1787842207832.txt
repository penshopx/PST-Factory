============================================================
1. PROJECT MISSION
============================================================

Build a NEW, STANDALONE web application called:

PST FACTORY

PST Factory is a product manufacturing platform for creating
Problem-Solving Toolkit (PST) products.

IMPORTANT:

This is a BRAND NEW REPLIT PROJECT.

Do not assume an existing codebase.
Do not integrate with an existing application automatically.
Do not copy another application's architecture.
Do not modify Gustafta.

PST Factory must be architected as an independent product.

============================================================
2. WHAT IS PST?
============================================================

PST means:

Problem-Solving Toolkit.

A PST is NOT simply:

- a chatbot
- an ebook
- a PDF
- a template bundle
- a collection of tools
- a generic AI assistant

A PST is:

"A structured digital problem-solving experience designed to
help a specific user solve a specific problem and achieve a
defined outcome."

The core principle is:

PROBLEM
→ PROCESS
→ OUTCOME

A PST may combine:

- practical guide
- mini module
- knowledge
- assessment
- checklist
- template
- worksheet
- calculator
- mini app
- AI assistant
- AI agent
- workflow
- report
- recommendation
- action plan

However:

NOT every PST must contain every component.

The Factory determines which components are necessary based
on the problem and desired outcome.

9. GUSTAFTA RELATIONSHIP
============================================================

Gustafta is an EXTERNAL ENGINE.

PST Factory is an independent application.

Conceptual architecture:

PST FACTORY
     │
     ↓
SERVICE / ADAPTER LAYER
     │
     ↓
GUSTAFTA ENGINE

PST Factory should be able to use Gustafta capabilities such
as:

- AI
- Knowledge Base
- Persona
- Agentic AI
- Memory
- Mini Apps
- Workflow/orchestration
- document processing

BUT:

Do not assume Gustafta APIs exist.

Do not invent endpoints.

Do not hard-code fake production integration.

Create an abstraction layer such as:

GustaftaEngine

Possible capabilities:

- generateAIResponse()
- retrieveKnowledge()
- invokeAgent()
- runMiniApp()
- getPersona()
- storeMemory()
- retrieveMemory()

The exact interface must be adjusted when actual Gustafta
API specifications become available.

For development, create:

MockGustaftaEngine

This allows PST Factory to function independently during
development.

The mock must be clearly identified as MOCK.

44. ENGINEERING PRINCIPLES
============================================================

Follow these principles:

1. Build the Factory, not a collection of PSTs.
2. Problem first, technology second.
3. Outcome first, feature count second.
4. Reuse before rebuild.
5. AI proposes; humans approve.
6. Structured data over uncontrolled text.
7. Configuration over hard-coded product logic.
8. External engine integration through adapters.
9. Do not invent Gustafta APIs.
10. Do not over-engineer the MVP.
11. Keep production versions immutable.
12. Security must be server-side.
13. Do not fabricate analytics.
14. Keep customer data isolated.
15. Design for future PST scale.

============================================================
45. SUCCESS DEFINITION
============================================================

The MVP is successful when:

An administrator can enter a problem and transform it into a
working PST product through the Factory.

The resulting PST can be:

- previewed
- tested
- QA'd
- approved
- published
- used by a customer

AND:

A second PST can reuse components from the first PST.

The most important metric is not:

"How many PSTs exist?"

The important metric is:

"How much faster can we build PST #2 than PST #1,
and PST #10 than PST #2?"
