============================================================
PART 1 — SECURITY BOUNDARY
============================================================

Before expanding manufacturing capabilities, establish proper
server-side ownership and access boundaries.

Introduce the concept:

USER
→ WORKSPACE
→ ROLE
→ PROJECT

Minimum roles:

ADMIN
EDITOR
VIEWER
CUSTOMER

ADMIN:
- manage workspace
- manage users/roles
- create/edit projects
- manage libraries
- approve
- publish

EDITOR:
- create projects
- edit projects
- run Architect
- edit Blueprint
- assemble
- simulate
- run QA

VIEWER:
- read-only Factory access

CUSTOMER:
- cannot access Factory management interfaces
- can only access explicitly published PST runtime experiences

============================================================
OWNERSHIP
============================================================

Add appropriate ownership/workspace relationships.

Projects must not be globally accessible merely because a user
is authenticated.

Every Factory resource that represents private manufacturing
data must have a server-side authorization boundary.

At minimum review:

- projects
- blueprints
- assets
- patterns
- recipes
- simulations
- QA runs
- factory events

Do not rely on frontend hiding.

Every protected API endpoint must verify:

1. authenticated actor
2. workspace membership
3. role
4. resource ownership/access

============================================================
CUSTOMER BOUNDARY
============================================================

Separate:

FACTORY MANAGEMENT
from
PUBLISHED CUSTOMER RUNTIME

A customer must NOT be able to access:

- draft projects
- factory settings
- internal assets
- internal patterns
- internal recipes
- internal QA data
- manufacturing events

Customer runtime should only resolve a valid PUBLISHED release.

Do not make the customer workspace publicly accessible unless
there is an explicit published access mechanism.

Create the architecture for:

Published PST
→ Release
→ Customer Runtime

Do not overbuild billing or customer account management.

============================================================
PART 2 — PST SCHEMA
============================================================

Introduce the concept:

PST SCHEMA

The PST Schema is the executable contract describing how a PST
behaves.

It must be more than metadata.

A PST Schema should describe:

1. Metadata
2. Problem
3. Target User
4. Inputs
5. Questions
6. Rules
7. Scoring
8. Knowledge
9. Workflow
10. AI
11. Outputs
12. Action Plan
13. Completion

The Schema must be structured and machine-readable.

Example conceptual structure:

PST
├── metadata
├── problem
├── user
├── inputs
├── questions
├── rules
├── scoring
├── knowledge
├── workflow
├── ai
├── outputs
├── actionPlan
└── completion

Do not put the entire executable behavior into an uncontrolled
JSON blob.

Use relational entities where relationships and identity matter.

Use JSON/JSONB only for genuinely flexible configuration.

Build an extensible foundation.

============================================================
PART 4 — QUESTION SCHEMA
============================================================

Questions must be structured.

A question should support:

- id
- label
- type
- required
- options
- validation
- scoring reference
- conditional visibility where appropriate

Questions must be usable by customer runtime.

The system must no longer treat questions as static descriptive
text only.

============================================================
PART 5 — RULES ENGINE FOUNDATION
============================================================

Introduce a simple configuration-driven rule model.

Example:

IF
cashflow_score < 40

THEN
condition = "HIGH_RISK"

Do not build a complex programming language.

Use a safe structured rule representation.

Rules must be data-driven.

The purpose is to prove that different PSTs can have different
logic without requiring product-specific code.

============================================================
PART 6 — SCORING MODEL
============================================================

Create a configurable scoring foundation.

Example:

Question A
→ weight 10

Question B
→ weight 20

Question C
→ weight 30

Calculate:

raw score
normalized score
classification

Example:

0–39 = HIGH_RISK
40–69 = MODERATE
70–100 = HEALTHY

Do not hard-code these values into the application.

The values must belong to the PST configuration.
