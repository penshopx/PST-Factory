Ini milestone yang sangat penting. **Task #42 sebaiknya sekarang di-freeze**, sama seperti #35 dan #40.

Kita sudah sampai pada titik di mana PST Factory bukan lagi sekadar punya data model, tetapi sudah memiliki **rantai manufacturing yang disiplin**:

```text
Release Snapshot
      ↓
Canonical Source V1
      ↓
Manufacturing IR V1
      ↓
Validator V1
      ↓
      ???
```

Yang `???` sekarang memang **Compiler v1**.

## Saya menyarankan jangan langsung Build Compiler

Sebelum coding Compiler, lakukan **Architecture Review Gate khusus Compiler**.

Karena Compiler adalah titik yang mengubah seluruh fondasi tadi menjadi produk yang benar-benar dapat dijalankan.

Target kontraknya harus dikunci terlebih dahulu:

```text
PstCanonicalSourceV1
        ↓
   Normalization
        ↓
PstManufacturingIRV1
        ↓
    Validator
        ↓
      PASS
        ↓
   PST Compiler V1
        ↓
ExecutablePstDefinitionV1
```

### Compiler harus sesederhana mungkin

Compiler **tidak boleh**:

* memanggil OpenAI;
* memanggil Gustafta;
* membaca database;
* mengambil asset terbaru;
* menentukan bisnis berdasarkan nama produk;
* mempunyai `if cashflow`;
* mempunyai `if decision`;
* mempunyai `if compliance`;
* menjalankan customer session.

Compiler hanya melakukan:

> **transformasi deklarasi yang sudah valid menjadi definisi PST yang executable.**

```text
ExecutablePstDefinitionV1

├── identity
├── schemaVersion
├── releaseVersion
├── inputs
├── states
├── journey
├── operations
├── rules
├── scoring
```

Misalnya:

```text

   ↓

   ↓
Calculate score
   ↓
Generate diagnosis
   ↓
Recommendation
   ↓

   ↓

```

Tetapi **konfigurasi setiap PST berbeda**.

# Acceptance yang lebih penting daripada unit test

Saya bahkan akan menjadikan ini sebagai **Compiler Proof Test**:

```text
                 ┌── Cashflow Configuration
                 │
Snapshot ────────┼── Decision Configuration
                 │
                 └── Compliance Configuration
                         ↓
                    SAME PIPELINE
                         ↓
                    SAME COMPILER
                         ↓
             ┌───────────┼───────────┐
             ↓           ↓           ↓
          PST-A        PST-B        PST-C
```

Kemudian kita cek:

| Pengujian                                     | Harus |
| --------------------------------------------- | ----- |
| Compiler menerima snapshot valid              | PASS  |
| Snapshot invalid                              | BLOCK |
| Cashflow menghasilkan executable definition   | PASS  |
| Decision menghasilkan executable definition   | PASS  |
| Compliance menghasilkan executable definition | PASS  |
| Struktur ketiga output valid                  | PASS  |
| Behavior berbeda berasal dari configuration   | PASS  |
| Product-specific branch                       | **0** |
| Provider/network call                         | **0** |
| Database dependency                           | **0** |

## Satu hal lagi: Compiler jangan langsung mengubah Runtime

Ini penting.

Kita ingin:

```text
Compiler
   ↓
Executable PST Definition
```

dulu.

Bukan:

```text
Compiler
   ↓
langsung utak-atik customer workspace
```

Karena kita ingin bisa menginspeksi hasil Compiler secara independen.

Misalnya Factory bisa memperlihatkan:

```text
COMPILE RESULT

PST: Cashflow Health Check
Compiler: v1
Schema: canonical-v1
Status: COMPILED

Inputs: 4
Steps: 7
Rules: 5
Outputs: 4
Actions: 3
```

Baru setelah itu Task Runtime mengonsumsi:

```text
ExecutablePstDefinition
```
