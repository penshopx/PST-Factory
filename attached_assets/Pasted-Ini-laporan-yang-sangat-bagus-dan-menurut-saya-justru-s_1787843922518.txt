# 2. Perubahan paling penting: Builder → PST Compiler

Menurut saya ini perlu menjadi konsep inti berikutnya.

Sekarang Builder masih seperti:

> "Saya punya blueprint, lalu saya rakit beberapa komponen."

Kita ingin menjadi:

> **"Saya punya Blueprint, lalu saya compile menjadi sebuah PST yang executable."**

Misalnya Factory mendapat:

### Problem

> Kontraktor tidak tahu apakah kondisi cashflow proyeknya sehat.

Architect menemukan:

```text
Pattern:
DIAGNOSIS

Recipe:
FINANCIAL_HEALTH_CHECK

Knowledge:
CASHFLOW_RULES

Assets:
Assessment
Scoring Engine
Recommendation Assistant
Action Plan
```

Blueprint:

```text
INPUT
 ↓
ASSESSMENT
 ↓
SCORING
 ↓
DIAGNOSIS
 ↓
RECOMMENDATION
 ↓
ACTION PLAN
```

Compiler menghasilkan:

```text
PST #001
Cashflow Health Check
```

Tanpa programmer membuat halaman khusus untuk PST tersebut.

**Nah, ini lompatan besar.**

# 3. Pattern harus berubah dari "catatan" menjadi mesin

Saat ini:

```text
Pattern
name
description
steps
```

Target:

```text
PATTERN: DIAGNOSIS

INPUT
 ↓
ASSESSMENT
 ↓
SCORING
 ↓
ANALYSIS
 ↓
RECOMMENDATION
 ↓
OUTPUT
```

Jadi Pattern memiliki struktur yang dapat dipakai Builder/Compiler.

Contoh lain:

### Decision Pattern

```text
Problem
 ↓
Options
 ↓
Criteria
 ↓
Scoring
 ↓
Comparison
 ↓
Recommendation
```

### Planning Pattern

```text
Goal
 ↓
Current State
 ↓
Gap
 ↓
Priority
 ↓
Plan
 ↓
Action
```

### Document Analysis Pattern

```text
Upload
 ↓
Extract
 ↓
Validate
 ↓
Analyze
 ↓
Score
 ↓
Report
```

Dengan demikian kita mulai mempunyai **Problem-Solving Grammar**.

# 4. Recipe adalah "formula produksi"

Ini bahkan lebih menarik.

Pattern:

> **bagaimana menyelesaikan jenis masalah**

Recipe:

> **kombinasi komponen untuk membuat produk tertentu**

Misalnya:

### RECIPE: BUSINESS HEALTH CHECK

```text
Profile
+
Assessment
+
Scoring
+
Knowledge Rules
+
AI Diagnosis
+
Recommendation
+
Action Plan
```

Kemudian:

### PST A

Cashflow Health Check

memakai Recipe tersebut.

### PST B

Business Readiness Check

juga memakai Recipe tersebut.

Tetapi input, knowledge, scoring rules, dan output-nya berbeda.

Jadi:

```text
RECIPE
   ↓
INPUT CONFIG
   ↓
KNOWLEDGE CONFIG
   ↓
RULE CONFIG
   ↓
OUTPUT CONFIG
   ↓
PST
```

**Inilah leverage Factory.**

# 5. Dan kita perlu satu konsep baru: PST Schema

Saya sangat menyarankan kita tambahkan konsep:

## PST Schema

Ini adalah kontrak yang menjelaskan **bagaimana sebuah PST berperilaku**.

Misalnya:

```text
PST Schema
│
├── metadata
├── problem
├── user
├── inputs
├── questions
├── rules
├── scoring
├── knowledge
├── workflow
├── AI
├── outputs
├── action_plan
└── completion
```

Dengan ini customer workspace tidak perlu tahu:

> "Ini Cashflow PST."

Workspace cukup tahu:

> "Ini adalah PST dengan schema tertentu."

Kemudian dia merendernya.

# 6. Inilah yang akan menjawab masalah "PST #10"

Kita buat eksperimen yang jauh lebih keras daripada PST #2.

Buat 3 PST:

### PST #001

**Cashflow Health Check**

### PST #002

**Decision Readiness Check**

### PST #003

**Document Compliance Check**

Ketiganya harus berbeda:

|           | PST 001          | PST 002           | PST 003           |
| --------- | ---------------- | ----------------- | ----------------- |
| Input     | Financial data   | Decision options  | Document          |
| Pattern   | Diagnosis        | Decision          | Document Analysis |
| Scoring   | Financial        | Decision          | Compliance        |
| Knowledge | Cashflow         | Decision criteria | Regulation        |
| Output    | Health diagnosis | Recommendation    | Compliance report |
| Workflow  | berbeda          | berbeda           | berbeda           |

**Dan tidak boleh menulis kode khusus untuk ketiga produk tersebut.**

Kalau berhasil:

> kita punya bukti bahwa PST Factory benar-benar configuration-driven.

# 8. Versioning juga penting sebelum kita punya banyak PST

Kita jangan sampai nanti:

```text
PST v1
   ↓
edit asset
   ↓
PST customer berubah
```

Itu berbahaya.

Yang kita inginkan:

```text
PST Project
     │
     ├── Draft v1.1
     │
     └── Published v1.0
              │
              └── Customer menggunakan v1.0
```

Kemudian:

```text
Draft v1.1
 ↓
QA
 ↓
Approve
 ↓
Publish
 ↓
v1.1
```

Customer berpindah ke versi baru secara terkendali.
